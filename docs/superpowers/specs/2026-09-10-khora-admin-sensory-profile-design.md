# KHORA Administración: Perfil sensorial de productos

**Fecha:** 2026-09-10
**Estado:** diseño aprobado para especificación; pendiente de aprobación final del documento antes de implementar

## 1. Contexto

KHORA Administración ya permite crear y editar productos, su descripción pública, notas privadas, receta, costos y márgenes. La descripción pública se persiste en `products.store_description` y se consume en KHORA Tienda.

El nuevo Perfil sensorial debe incorporarse al formulario de producto sin duplicar ese contenido ni modificar la arquitectura comercial existente. El perfil será información estructurada y reutilizable, preparada para una futura presentación pública y para un futuro recomendador de aromas, pero este alcance implementa únicamente la gestión administrativa.

La aplicación utiliza Next.js, un route handler central en `/api/khora` y consultas PostgreSQL del lado servidor. Los productos y combos comparten la tabla `products`, pero tienen flujos de edición distintos. Esta funcionalidad se limitará a productos y no alterará el formulario de combos.

## 2. Objetivos

- Permitir asignar a cada producto uno o varios valores sensoriales controlados.
- Evitar texto libre y valores duplicados para datos que luego deberán filtrarse o puntuarse.
- Mantener la descripción pública existente dentro del bloque sensorial, sin cambiar su almacenamiento.
- Mostrar una vista previa compacta y en vivo dentro del formulario.
- Mantener compatibilidad total con productos existentes que no tengan perfil sensorial.
- Respetar la seguridad actual: lectura y escritura mediante el backend, sin acceso público directo a las nuevas tablas.
- Dejar una base de datos apta para una futura experiencia pública sin implementar esa experiencia ahora.

## 3. Fuera de alcance

Esta etapa no incluye:

- la experiencia pública “Encontrá tu aroma”;
- la guía de aromas en KHORA Tienda;
- cambios en las fichas públicas de productos;
- cambios en búsqueda, stock, reservas, pedidos, ventas o precios;
- perfiles sensoriales para combos;
- generación de textos o recomendaciones con inteligencia artificial;
- un nuevo modelo de visibilidad Minorista/Mayorista/Ambos;
- una pantalla para administrar el catálogo de opciones sensoriales.

## 4. Modelo de datos

### 4.1. Catálogo controlado: `sensory_options`

Tabla que contiene todos los valores disponibles.

| Campo | Tipo | Regla |
| --- | --- | --- |
| `id` | `integer generated by default as identity` | clave primaria; consistente con los IDs del esquema actual |
| `kind` | `text` | obligatorio; uno de `FAMILY`, `NOTE`, `SENSATION`, `INTENSITY`, `ROOM`, `MOMENT` |
| `slug` | `text` | obligatorio, estable y sin acentos |
| `label` | `text` | obligatorio; texto visible |
| `sort_order` | `integer` | obligatorio, valor por defecto `0` |
| `active` | `boolean` | obligatorio, valor por defecto `true` |
| `created_at` | `timestamptz` | obligatorio, `now()` |
| `updated_at` | `timestamptz` | obligatorio, `now()` |

Restricciones e índices:

- `CHECK` sobre `kind` con los seis tipos permitidos.
- `UNIQUE (kind, slug)` para impedir duplicados dentro de un tipo.
- `UNIQUE (id, kind)` para permitir que la relación valide simultáneamente el ID y el tipo.
- índice por `(kind, active, sort_order)` para cargar el catálogo ordenado.

Los slugs son identificadores estables. Cambiar una etiqueta en el futuro no modifica relaciones ni contratos.

### 4.2. Relación producto-opción: `product_sensory_options`

| Campo | Tipo | Regla |
| --- | --- | --- |
| `product_id` | `integer` | FK a `products(id)` con `ON DELETE CASCADE` |
| `option_id` | `integer` | identifica la opción |
| `kind` | `text` | replica el tipo para reforzar restricciones e índices |
| `sort_order` | `integer` | obligatorio, valor por defecto `0`; conserva el orden elegido cuando corresponda |
| `created_at` | `timestamptz` | obligatorio, `now()` |

Restricciones e índices:

- clave primaria `PRIMARY KEY (product_id, option_id)`.
- FK compuesta `(option_id, kind)` hacia `sensory_options(id, kind)` para impedir asociaciones con un tipo incorrecto.
- índice `(product_id, kind, sort_order)` para reconstruir el perfil.
- índice `(option_id, product_id)` para futuras consultas inversas.
- índice único parcial sobre `(product_id, kind)` cuando `kind IN ('INTENSITY', 'MOMENT')`, garantizando una sola intensidad y un solo momento por producto incluso si un cliente elude la interfaz.

No se crea una tabla adicional `product_sensory_profiles`: el perfil existe como el conjunto de relaciones. La descripción pública sigue en `products.store_description`, evitando dos fuentes de verdad.

### 4.3. Valores iniciales

La migración inserta los valores iniciales de forma idempotente mediante `(kind, slug)`:

- Familias: Dulce, Fresca, Cítrica, Floral, Amaderada, Especiada, Frutal, Herbal, Ambarada.
- Notas: Vainilla, Ámbar, Sándalo, Lavanda, Jazmín, Limón, Naranja, Bergamota, Rosa, Coco, Canela, Cedro, Eucalipto.
- Sensaciones: Relajante, Energizante, Acogedora, Elegante, Fresca, Sofisticada, Cálida, Limpia.
- Intensidad: Suave, Media, Intensa.
- Ambientes: Living, Dormitorio, Baño, Cocina, Oficina, Comedor, Espacios de relax, Local comercial.
- Momento: Día, Noche, Todo el día.

Los slugs se normalizan en minúsculas ASCII, por ejemplo `citrica`, `ambar`, `sandalo`, `espacios-de-relax` y `todo-el-dia`.

### 4.4. Seguridad

- Se habilita RLS en ambas tablas nuevas.
- Se revocan permisos directos de `PUBLIC`, `anon` y `authenticated`.
- Se revocan esos mismos roles de las secuencias identity.
- Se conceden a `service_role` solamente los permisos de tabla y secuencia necesarios para tareas de servidor.
- No se crean políticas permisivas para navegación pública.
- La administración continúa accediendo mediante `/api/khora` y la conexión PostgreSQL segura del servidor.
- Ningún secreto ni credencial se incorpora a componentes cliente.

La migración es aditiva: no elimina ni transforma datos existentes. Los productos actuales comienzan con un perfil vacío.

## 5. Contratos del backend

### 5.1. Catálogo sensorial

Se agrega `GET /api/khora?entity=sensory_options`.

Respuesta exitosa:

```json
{
  "options": [
    {
      "id": 1,
      "kind": "FAMILY",
      "slug": "dulce",
      "label": "Dulce",
      "sort_order": 10
    }
  ]
}
```

Solo devuelve opciones activas, ordenadas por tipo, `sort_order` y etiqueta.

### 5.2. Carga de la definición de producto

La respuesta existente de `GET /api/khora?entity=product_definition&id=...` incorpora:

```json
{
  "sensory_profile": {
    "families": [1, 2],
    "notes": [10, 11],
    "sensations": [20],
    "intensity": 30,
    "rooms": [40, 41],
    "moment": 50
  }
}
```

Los campos múltiples siempre son arrays. `intensity` y `moment` son un ID o `null`. Si el producto no tiene relaciones, se devuelve la misma estructura vacía, no se omite el campo.

### 5.3. Guardado

Las acciones existentes `save_product_with_recipe` y `update_product_definition` reciben un campo adicional:

```json
{
  "sensoryProfile": {
    "families": [1, 2],
    "notes": [10, 11],
    "sensations": [20],
    "intensity": 30,
    "rooms": [40, 41],
    "moment": 50
  }
}
```

El backend debe:

1. aceptar un perfil vacío para compatibilidad;
2. exigir arrays en los campos múltiples;
3. aceptar `null` en intensidad y momento;
4. convertir IDs numéricos válidos y rechazar valores no enteros;
5. eliminar duplicados sin alterar el primer orden elegido;
6. comprobar que cada ID existe, está activo y pertenece al `kind` esperado;
7. rechazar más de una intensidad o momento antes de persistir;
8. rechazar el perfil sensorial si el registro editado es un combo;
9. reemplazar las asociaciones anteriores dentro de la misma transacción que guarda la definición y la receta.

Para compatibilidad con clientes anteriores, la ausencia total de `sensoryProfile` tiene una semántica distinta de un perfil explícitamente vacío: al editar, un campo ausente conserva las asociaciones existentes; un perfil enviado con todos sus campos vacíos las elimina. Al crear, un campo ausente equivale a no crear asociaciones.

Si falla cualquier validación, no se persiste parcialmente ni el producto, ni la receta, ni el perfil. La API responde con el formato de error existente y un mensaje accionable para la administración.

No se confía en etiquetas, slugs ni tipos enviados por el cliente; solo en IDs verificados contra el catálogo del servidor.

### 5.4. Observabilidad

Los logs del servidor pueden registrar acción, ID de producto y cantidad de selecciones por tipo. No deben registrar credenciales, cabeceras de autorización ni duplicar la descripción o las notas privadas.

## 6. Diseño de la interfaz administrativa

### 6.1. Ubicación

En el drawer existente para crear o editar un producto, el orden será:

1. información y definición actual del producto;
2. Perfil sensorial;
3. notas privadas;
4. receta, costos y márgenes actuales.

La descripción pública se mueve visualmente desde el bloque compartido actual al final de Perfil sensorial, pero sigue usando el mismo estado y la misma columna `products.store_description`. Las notas privadas permanecen en su propio bloque y en `code_base.description`.

El formulario de combos no cambia.

### 6.2. Componentes

Se incorporan componentes separados para evitar seguir ampliando el archivo monolítico:

- `SensoryProfileEditor`: orquesta todos los campos y expone un valor controlado.
- `SensoryChipGroup`: selección múltiple o única con chips accesibles.
- `AromaNotesSelector`: buscador local sobre el catálogo de notas, lista filtrada y chips seleccionados.
- `SensoryProfilePreview`: resumen visual en vivo, solo lectura.

Los tipos, constantes de `kind`, valor vacío y funciones de normalización se ubican en un módulo de dominio reutilizable, separado del JSX.

### 6.3. Campos

- **Familia olfativa:** selección múltiple con chips.
- **Notas aromáticas:** campo de búsqueda, resultados seleccionables y chips removibles. No ofrece creación de opciones libres.
- **Sensación:** selección múltiple con chips.
- **Intensidad:** selección única con chips o radios visuales.
- **Ambiente ideal:** selección múltiple con chips.
- **Momento recomendado:** selección única con chips o radios visuales.
- **Descripción pública:** textarea existente, ubicado al final del bloque.

Todo el perfil es opcional en esta etapa. Esto permite guardar productos antiguos o incompletos sin bloquear el flujo actual.

### 6.4. Vista previa

La vista previa se actualiza con el estado local del formulario, sin solicitudes adicionales. Muestra únicamente filas con datos y utiliza las etiquetas del catálogo ya cargado. No intenta simular la ficha de KHORA Tienda ni introduce una promesa visual pública todavía inexistente.

En desktop se presenta de forma compacta junto a los controles cuando haya ancho suficiente. En mobile se apila debajo, con chips que envuelven líneas y sin desplazamiento horizontal.

### 6.5. Estados y accesibilidad

- El editor permanece deshabilitado mientras carga el catálogo necesario.
- Si falla la carga, muestra un error específico y permite reintentar sin cerrar el formulario.
- Los chips son botones `type="button"` con `aria-pressed`.
- Los grupos usan etiquetas y relaciones accesibles; la selección única mantiene semántica equivalente a radio.
- El selector de notas se opera con teclado y conserva visibles las notas elegidas aunque cambie el texto de búsqueda.
- Al guardar, se reutiliza el bloqueo actual del formulario para evitar envíos dobles.
- Los errores del servidor aparecen en el área de error existente sin perder el contenido ingresado.

## 7. Flujo de datos

### Crear producto

1. El drawer carga materiales, mezclas y catálogo sensorial en paralelo.
2. El formulario inicia un perfil vacío.
3. El usuario selecciona valores y completa la descripción pública si corresponde.
4. El submit envía producto, receta y perfil en una única solicitud.
5. El servidor valida el catálogo, crea el producto y guarda asociaciones en una transacción.
6. Solo después del commit se actualiza la lista administrativa.

### Editar producto

1. El drawer carga el catálogo sensorial y `product_definition`.
2. Reconstruye el valor controlado con `sensory_profile`.
3. El usuario modifica selecciones.
4. El servidor valida y reemplaza las asociaciones dentro de la transacción existente.
5. Al reabrir el producto, las selecciones y su orden se mantienen.

## 8. Compatibilidad y migración

- No se requiere backfill de perfiles.
- La descripción pública existente se conserva sin cambios de columna ni contenido.
- Un producto sin asociaciones se comporta exactamente como antes.
- El guardado de recetas, costos, stock e historial conserva sus reglas actuales.
- El despliegue puede aplicar primero la migración y luego el código, porque las tablas son nuevas y no son consumidas por la versión anterior.
- Revertir el código no afecta los productos existentes; las nuevas tablas pueden permanecer sin uso.

## 10. Estrategia de pruebas

### Automatizadas

- La migración crea ambas tablas, sus FKs, unicidad parcial, índices y RLS.
- Las semillas contienen todos los valores iniciales sin duplicados de `(kind, slug)`.
- `anon` y `authenticated` no reciben acceso directo.
- La normalización acepta perfiles vacíos, deduplica IDs y conserva orden.
- IDs inexistentes, inactivos o de otro tipo producen error sin escritura parcial.
- Intensidad y momento admiten cero o una selección.
- Crear y editar un producto incluye las asociaciones en la transacción.
- La carga de un producto antiguo devuelve el perfil vacío normalizado.
- El flujo de combos no recibe ni renderiza el editor sensorial.
- La descripción continúa guardándose exclusivamente en `products.store_description`.

### Verificación manual

- Crear un producto sin perfil.
- Crear un producto con todas las categorías completas.
- Editar, quitar y reordenar selecciones; cerrar y reabrir el drawer.
- Buscar notas con y sin coincidencias y operar los chips con teclado.
- Simular una respuesta inválida y confirmar que el formulario conserva datos.
- Revisar el drawer en desktop y en un viewport móvil sin scroll horizontal.
- Ejecutar los tests, lint y build disponibles del proyecto.
- Confirmar que KHORA Tienda, combos, recetas, stock y pedidos no cambiaron.

## 11. Criterios de aceptación

- El formulario de producto contiene un bloque claro llamado “Perfil sensorial”.
- Todas las opciones provienen del catálogo controlado.
- Familia, notas, sensaciones y ambientes aceptan selección múltiple.
- Intensidad y momento aceptan una sola selección.
- La descripción pública aparece al final del perfil y mantiene su persistencia actual.
- Las notas privadas siguen separadas y no se exponen en el perfil.
- La vista previa refleja inmediatamente los valores seleccionados.
- Los productos existentes se editan y guardan aunque no tengan perfil.
- El formulario de combos permanece intacto.
- La API valida del lado servidor y guarda todo atómicamente.
- Las nuevas tablas no tienen acceso directo público.
- La interfaz funciona en desktop y mobile sin desbordamiento horizontal.
- Toda la suite existente continúa pasando.

## 12. Preparación para etapas futuras

Una futura etapa de KHORA Tienda podrá consultar estos datos desde un endpoint público que exponga únicamente etiquetas sensoriales de productos publicados. El futuro recomendador podrá puntuar coincidencias por IDs o slugs estables. Ninguna de esas rutas, vistas ni reglas de puntuación forma parte de esta implementación.
